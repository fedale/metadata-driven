# Languages

Every text the users read in the metadata can be translated: the labels of the objects and
fields, the options of a choice, the titles of the composite forms and of their sections, and
texts of your own placed in the layouts. Each user reads the application in their language.

- The metadata is written in the **default language**, English (`en`). Its labels are the texts
  of that language: nothing changes for a key with no translation.
- A **translation** gives a key a text in another enabled language (`it`). Translations live in
  the database, like the metadata: they are edited at runtime, from **Admin > Translations** or
  the console, without a deploy.
- A **text** is a key of its own, `text.<name>`, placed in a layout or a grid heading with a
  `{t:<name>}` token. It is written in the default language, and in the others if you like.

The texts of the application itself ("Save", "Cancel", "Required field") are not part of the
metadata: they are in Symfony translation files, shipped with the code (see
[The texts of the application](#the-texts-of-the-application)). The grid's own texts (pagination, filters, search, export) come with
fedale/gridview-bundle, which ships English and Italian.

## A first translation

Take a `pet` object: labels `Pet` / `Pets`, a `name` field labelled `Name`, a `species` choice
with the options `dog` (`Dog`) and `cat` (`Cat`).

**From the admin UI:** open **Admin > Translations**, which opens on **Metadata** into Italian.
Each key shows its English text, with a link to where it is defined, and an input. Type `Animali`
for `object.pet.plural`, `Nome` for `field.pet.name` and `Cane` for `option.pet.species.dog`, then
save.

**From the console:**

```bash
symfony console metadata:translation:set it object.pet.plural Animali
symfony console metadata:translation:set it field.pet.name Nome
symfony console metadata:translation:set it option.pet.species.dog Cane
symfony console metadata:translation:list it --missing      # what is left to translate
```

Then pick **IT** in the top bar: `/o/pet` is titled "Animali", the column is "Nome", the dog is
"Cane", and the grid's own texts are in Italian ("Cerca…"). The keys left untranslated keep
their English text.

## Keys

The key of a text says where it is defined. Admin > Translations and
`metadata:translation:list` show every key of the metadata, with its text.

| What | Key | Example |
|---|---|---|
| Object, singular and plural label | `object.<object>.singular`, `object.<object>.plural` | `object.pet.plural` |
| Field label | `field.<object>.<field>` | `field.pet.name` |
| Option of a choice | `option.<object>.<field>.<value>` | `option.pet.species.dog` |
| Inverse label of a relation (the list of records pointing at a record) | `inverse.<object>.<field>` | `inverse.pet.owner` |
| Pattern message of a text field | `message.<object>.<field>` | `message.profile.zipcode` |
| Composite form title | `form.<form>` | `form.registration` |
| Section of a composite form (names from the root down) | `section.<form>.<section>[.<section>...]` | `section.registration.profile.phones` |
| Description of the root of a composite form, or of a section | `description.<form>[.<section>...]` | `description.registration.profile` |
| Service field of a composite form | `service.<form>[.<section>...].<field>` | `service.registration.terms` |
| A text of your own | `text.<name>` | `text.sign_in` |

The inverse label, the pattern message and a description have a key only when one is set.

## Texts in layouts: `{t:name}`

A layout is HTML written once, in one language. To make a word of it translatable, create a text
and place it with a token:

```html
<fieldset>
    <legend>{t:sign_in}</legend>
    {username} {email} {password}
</fieldset>
```

1. Create the text: **Admin > Translations > Texts > New text**, name `sign_in`, English
   `Sign in`, Italian `Accesso`; or from the console:

   ```bash
   symfony console metadata:translation:set en text.sign_in "Sign in"
   symfony console metadata:translation:set it text.sign_in Accesso
   ```

2. Place `{t:sign_in}` in the layout and save it.

A `{t:name}` token works in:

- a form view (see [Views](views.md#writing-a-layout));
- the `layout` of any node of a composite form (see [Composite forms](forms.md#layouts));
- the `label` of a column of a grid view, e.g. `{ field: name, label: '{t:pet_name}' }` (see
  [Grid views](views.md#grid-views)).

The text replaces the token in the user's language, escaped: `Sign in & data` shows as text,
never as HTML. A token may also sit in an attribute, e.g. `<section title="{t:help}">`, unlike a
`{field}` token. The text is shown in the default language while it has no translation.

## The admin pages

**Admin > Translations** has two tabs, one per kind of text:

- **Metadata**: the labels of the metadata (objects, fields, options, inverse labels, pattern
  messages, composite forms and their sections), grouped by object and by form, translated into
  one language at a time (Italian; with more languages, a switch picks it). Each row has the
  key, the English text with an **Edit** link to the object, field or form that defines it (that
  is where the English text changes), and the Italian input. Empty an input to remove the
  translation.
- **Texts**: your own `{t:name}` texts, not tied to any metadata: one row each, with an input
  per language side by side and where each one is placed. English is required; emptying it
  removes the text in every language, once no token places it. **New text** creates one.

## The texts of the application

The pages for the users (top bar, sign-in, record lists and forms, composite forms) take their
own texts from `translations/messages.<locale>.yaml`: `messages.en.yaml` and
`messages.it.yaml`. They are part of the code: change them in the files, not in the admin. A
key missing in a language shows its English text.

The admin pages are still in English only.

## Languages of the users

The language of a page is, in order:

1. the one the user picked in the **top bar** (EN / IT), saved in their profile;
2. otherwise the best match of the browser's languages (the `Accept-Language` header) among the
   enabled ones;
3. otherwise the default language.

The sign-in page follows the browser. The page tells its language in `<html lang>`, which the
grid follows too.

## Configuring the languages

The languages are set in `config/packages/translation.yaml`:

```yaml
framework:
    default_locale: en          # the language the metadata is written in
    enabled_locales: [en, it]   # the languages a user can pick, in the order of the top bar
```

**Adding a language**, e.g. French: add it to the list (`[en, it, fr]`) and run
`symfony console cache:clear`. It appears in the top bar, in the language switch of Admin >
Translations > Metadata, as an input of each text, and in the console commands. Two things it does not bring by itself:

- the grid's own texts: fedale/gridview-bundle ships `en` and `it` only, and falls back on the
  default language; add `translations/GridviewBundle.fr.yaml` to the app (same keys as the
  bundle's `GridviewBundle.it.yaml`) to translate them;
- the texts of the application itself: add `translations/messages.fr.yaml` (same keys as
  `messages.en.yaml`).

**Changing the default language** changes what the metadata is taken to be written in: do it
before translating. The rows already stored in the new default language are not used any more
(except the texts), and the labels should be in that language.

## Rules

| Rule | Error |
|---|---|
| The key is one of the metadata | `"field.pet.nickname" is no key of the metadata (see Admin > Translations for the keys).` |
| A key of the metadata takes no text in the default language: its label is the text | `In en, the text of "field.pet.name" is the one of the metadata: change the label itself.` |
| The language is enabled | `"fr" is no enabled language (en, it).` |
| A text has its default-language text before the others | `The text "text.welcome" is not defined: give it a text in en first.` |
| A text name: 1 to 50 lowercase letters, digits and single underscores, starting with a letter | `Invalid text "text.Bad-Name"...` |
| A `{t:name}` token names an existing text, when its layout or grid view is saved | `View "main": {t:sign_in} is no text: define "text.sign_in" in en first (Admin > Translations > Texts).` |
| A text still placed by a token cannot be removed | `{t:sign_in} is still placed by form registration: remove the tokens first.` |

An empty text removes the translation. Removing the default-language text of a text key removes
the text in every language.

## Under the hood

| Piece | Where |
|---|---|
| Storage | `core.metadata_translation`: `locale`, `message_key`, `text`; unique on `(locale, message_key)`. A user's language: `core.user_profile.locale` (null: the browser's) |
| Keys | `TranslationKey` (Metadata Contract) builds them; `TranslationKeys` lists those of the metadata, with their text, and where each `{t:name}` is placed |
| Changes | `MetadataManagerInterface::translate($locale, $key, ?$text)` (`TranslateHandler`), used by the admin UI and the console. It dispatches `MetadataChanged`: the cached texts go with the cached metadata |
| Admin read side | `MetadataTranslationsInterface`: `entries($locale)` (every key with its translation), `texts()` (every text in every language) |
| Pages read side | `LocalizedMetadataRegistry`: the metadata with the texts of the request's language (`MetadataTranslator`), cached per language (`TranslationCatalog`, same pool and tag as the snapshot) and per request |
| Who reads it | The record pages, the composite forms and the record validation, with `#[Target('localizedMetadata')] MetadataRegistryInterface`. Every other service (admin, compilers, schema) reads the metadata as written, so a translation is never saved back as a label |
| The user's language | `UserLocale` (User module) switches the request after the firewall, through `LocaleSwitcher`; `/account/locale` (`AccountController`) saves the choice of the top bar |
| Checks on save | `DefinedTexts`, called by the form views, the composite form compiler and the grid view compiler |

Deleting a composite form deletes the translations of its keys. The translations of a field
option removed later stay in the table, unused, and come back if the option does.
