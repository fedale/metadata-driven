# Project status and working notes

Internal notes for whoever (human or agent) picks the work up, on any machine. Read this before
starting a task; update it in the same branch whenever a decision is taken, a feature lands or the
work queue changes. The user-facing documentation is in [../README.md](../README.md).

Last updated: 2026-11-12.

## Setting up on a new machine

- The bundles and the format come from Packagist (since 2026-11-07): `composer install` is
  enough. To work on one, clone it next to this repository and `composer link ../<repo>`
  (the composer-link plugin, installed globally; see getting-started.md, "Working on the
  bundles"). All the repositories are under `git@github.com:fedale/<repo>.git`, cloned under
  the name of their repository (the format: `../metadata-driven-template-format`, the name of
  its package too); use SSH remotes.
- Then follow [../getting-started.md](../getting-started.md) (`make up`, `make db`, `make assets`).
- The dev database is not in git. The "registration" model built on the original machine (objects
  `account`, `profile`, `phone`, `qualification`, `region`, `province`, `municipality` loaded from
  the ISTAT CSV, form `registration`) exists only there: a new machine starts empty. On
  2026-11-10 it was rebuilt on the second machine's dev database from the specification in
  `tests/Support/CreatesRegistrationForm.php`, on top of `fedale/geo-italy` installed from the
  catalog, and exported as `fedale/registration` 1.0.0 (see template-plan.md, phase 8, step 7).
  Installing both templates is how a new machine gets it now.

## Working rules agreed with the user

- One phase or work item at a time, each on its own branch; wait for the user's review before
  starting the next one. Merge with `--no-ff` ("Merge branch 'x'"), delete merged branches.
- Sessions working in parallel (two agents, or an agent and the user) each use a `git worktree`
  of their own: in a shared checkout a branch switch carries the other session's uncommitted
  changes along, and both end up editing the same files. Put it next to this repository
  (`git worktree add ../metadata-driven-<topic> -b <branch> main`: `composer link ../<repo>`
  then works there as in the main checkout), then in it: `composer install` (plus `composer
  link ../<repo>` for a bundle the work changes), `php bin/console importmap:install`,
  `symfony console sass:build`, and `COMPOSE_PROJECT_NAME=metadata-driven` in the environment,
  so the Symfony CLI finds the running database of the main checkout. For tests of its own, a
  `.env.test.local` with `TEST_TOKEN=_<topic>` (database `app_test_<topic>`, through
  `dbname_suffix`; without the Symfony CLI also the `DATABASE_URL` of the main checkout, from
  `symfony var:export DATABASE_URL` there), created and migrated as `make db-test` does. Never
  `make up` (nor `make test` or `make qa`, which call it) from a worktree: Docker Compose names
  the project after the directory and would start a second database on the fixed port 5432. Run
  `make cs phpstan deptrac` and `php bin/phpunit` instead.
- Commit or push only when the user asks.
- Never run `rm`: finish the task and list the paths the user should delete by hand.
- Every change ships with its docs in the same branch: the topic page in `docs/`, the cross
  references (`docs/README.md`, `admin.md`, `console.md`, "Not yet" notes), the bundle's `docs/`
  when a bundle changes, and this file.
- Run `make qa` before reporting a task as done. Tests need the Symfony CLI
  (`symfony php bin/phpunit` / `make`) to get the Docker `DATABASE_URL`.
- Browser checks: never seed the dev database (objects created there cannot be removed without
  `metadata:purge`). Use a throw-away database with `APP_ENV=prod APP_DEBUG=1 APP_SECRET=…` and
  `php -d variables_order=EGPCS -S …`, and run commands with `php bin/console` (with the copy's
  `DATABASE_URL`): `symfony console` ignores it and hits the dev database.
- `config/reference.php` is regenerated by the cache warmup: do not commit changes that come from
  a bundle's uncommitted work.

## Architecture decisions

- Symfony 8.x (not 7.4 LTS), PostgreSQL 17, single-tenant first.
- Modules under `src/Module/<Name>/{Contract,Domain,Application,Infrastructure,UI}`; two Deptrac
  rulesets (layers, modules); a module only sees the other modules' `Contract`.
- Reused bundles (the user's own projects): `fedale/gridview-bundle` (grids and generic form
  components), `fedale/setting-bundle` (UI settings), `fedale/rbac-bundle` (permissions).
- CSS: generic form components live in gridview-bundle with the `gv-` prefix and `--gv-*` tokens;
  app-specific components use `md-` BEM in `assets/styles/app.css`, colours only from `--gv-*`
  tokens.
- Default locale `en`, enabled `[en, it]` (the user rejected Italian as default).
- Relations: many-to-one plus read-only inverse one-to-many. `onDelete` per field (`set_null`
  default, `restrict`, `cascade`) applied by the app because of soft delete. Many-to-many is a
  field type of its own, `many_to_many`, stored in a link table, `onDelete` `unlink` or
  `restrict` (no cascade), inverse read-only; see [many-to-many-plan.md](many-to-many-plan.md).
- Saved grid views are the bundle's client-side saved searches; server-side saved views are a
  possible later step.
- Lifecycle: archive keeps data and can be restored; purge only from the CLI
  (`metadata:purge`); rename rewrites hand-written views and forms (YAML comments are lost).

## Implementation notes

Things that are not obvious from a single file, and that are easy to break.

- **Metadata cache** (`Metadata/Infrastructure/Cache/CachedMetadataRegistry.php`): the snapshot
  key (`metadata_snapshot.vN`) and the forms key (`metadata_forms.vN`) are versioned. Bump the
  version whenever the shape of a cached DTO changes, and bump the key that holds that DTO: a
  form DTO (e.g. `ServiceFieldDto`) lives under the forms key, not the snapshot key. The snapshot key also carries a fingerprint
  of every field type's default settings, so adding a setting renews the snapshot by itself.
  Every metadata key (snapshot, forms, translations) carries `MetadataRevision::current()`, the
  instance's id and the revision of `core.metadata_state`, which statement-level triggers on the
  five `core.metadata_*` tables bump. **A new metadata table needs the trigger too** (see
  migration `Version20261107060749`), or its changes stay unseen by the other servers. The
  revision is read before the item it keys: never reverse that order.
- **Localized metadata**: `LocalizedMetadataRegistry` (`#[Target('localizedMetadata')]`) returns
  metadata with labels in the user's locale; only the Record and Validation modules use it. Metadata
  text is the default-locale fallback; translations live in `core.metadata_translation`.
- **Transactions**: `Shared/Transaction/TransactionRunner` uses DBAL `transactional()`, not the
  EntityManager's `wrapInTransaction()`, which closes the EntityManager on domain exceptions.
- **Metadata writes** go through `MetadataManagerInterface` (Metadata Contract): it validates the
  commands and throws `MetadataInputInvalid` with errors keyed by field. The admin forms for field
  settings are generated from `FieldTypeInterface::settingDefinitions()`.
- **Field types** (`FieldTypeInterface`): `defaultValue()`, `isWriteOnly()`, `toStorage()`; the
  snapshot loader merges each type's default settings. Passwords are hashed through
  `SecretHasherInterface` ("record_secret" hasher), write-only, blank on update keeps the value.
- **Relations**: their config lives in field settings (`RelationSettings`), there is no relation
  table. A `many_to_many` field (`ManyToManySettings`) has no column: `FieldDefinitionDto::
  storesColumn()` is false and every module touching columns must skip it; its link table
  (`DataSchema::linkTable()`) is built, renamed and dropped by the Schema module with the object,
  and read and written by the Record store (`replaceLinks()`, links loaded with the record) and
  read by the grid source (labels and ids in correlated subqueries, filter as `EXISTS`), both
  through `LinkSource` (`RecordTable::links()`): no SQL names the link table by hand. With
  `through`, the links are the live records of a junction object: no link table, `andLive()` on
  every read, writes refused (they are junction records), the junction's relations carry the
  delete rules. A `file` field with `multiple: true` (`FileListSettings`, `fileList()`) has no
  column either, and a link table of its own (`target_id` → `core.file`, plus `position`):
  code handling links must tell the two apart with `manyToMany()` / `fileList()`, never with
  `!storesColumn()` alone. A file list is read and written by the Record store too
  (`replaceFiles()`, read with the record, in `position` order) through
  `RecordTable::fileListTable()`, not `LinkSource`; its ids must be files the record already
  holds (`RecordManager::checkHeldFiles()`), uploads aside.
  Cascading selects use `dependsOn`/`dependsVia`; the lookup takes
  `filter[<field>]=<id>` (empty means no results) and the validator checks parent membership.
- **System columns** (`ObjectDefinition::SYSTEM_COLUMNS`, built by `TableDefinitionFactory`):
  `id`, `created_at`, `updated_at`, `created_by`, `deleted_at`, `sort`. Field names may not
  shadow them. Only the first three are read into `RecordOutput`; `deleted_at` is the soft
  delete filter; `created_by` is never written yet; `sort` (`INTEGER NOT NULL DEFAULT 0`, for
  a manual order, negatives allowed) is not read, written nor sorted on yet.
- **Search**: trigram GIN indexes on `LOWER(col)` are managed by `TrigramIndexPlanner` and kept out
  of the DBAL schema comparison.
- **Unique together** (`ObjectDefinition::$uniqueTogether`): partial unique indexes (`WHERE
  deleted_at IS NULL`, unlike single-field uniques), planned by `UniqueTogetherIndexPlanner` by
  name prefix `uniqc_` and hidden from the DBAL comparison, as `TrigramIndexPlanner` does for
  `trgm_`. A new planned index kind needs the same treatment in `DbalSchemaSynchronizer`.
- **Grid**: `DbalRecordGridSource` + `RecordGridFactory` (Record module). The bundle's columns
  are sortable by default: a column that must not sort needs `sortable(false)`. Grid views are at
  `/o/<object>/grid/<name>` because the bundle owns `?view=`; YAML compiled by `GridViewCompiler`,
  cells rendered by `CellRendererInterface` implementations.
- **Composite forms**: YAML compiled by `FormDefinitionCompiler` into JSONB
  (`core.metadata_form`); `CompositeRecordManager` checks the whole tree first, then writes it in
  one transaction. The compiler refuses a `fields` list that omits a field the object requires.
- **Lifecycle**: archive is refused while the item is used anywhere; `MetadataUsages` lists the
  uses.
- **Access**: permissions are `record.<object>.<read|create|update|delete>` and `admin.metadata`;
  controllers check them through `AccessCheckerInterface`. The user provider reloads RBAC roles on
  every request, and a role change signs the user out (`isEqualTo` compares sorted roles). The RBAC
  cache is disabled in the test env (`config/packages/fedale_rbac.yaml`) because tests roll back
  transactions.
- **Files** (`File` module): bytes in the `record_files` Flysystem storage under
  `<sha256[0:2]>/<sha256>`, one `core.file` row per stored file. Several rows may share the bytes,
  so whatever deletes bytes must first check that no row uses the key. The tests use the memory
  adapter (`when@test` in `config/packages/flysystem.yaml`). A file field's value is a
  `FileUpload` (new), the id of a stored file (kept) or null; `toStorage()` stores the upload,
  so a write that fails after it leaves an orphaned file (a `core.file` row, or only its bytes when
  a transaction rolls back) for the GC (`metadata:files:gc`), never a record pointing at nothing.
  The GC finds the references in the foreign keys to `core.file` (catalog), so a new table
  referencing files needs such a key. `store()` and the GC share an advisory lock per SHA-256
  (`ContentLock`): never write or delete content bytes without it. A file id given to a record
  (one file or a list) must be one the record holds (`RecordManager::checkHeldFiles()`): new
  files arrive only as uploads. The grid source
  looks the files of a page up in one `FileStorageInterface::findMany()` call (core.file belongs
  to the File module: no SQL join on it from Record) and hands each row `<field>__file`, a list
  of `{id, name, image}` (every file of a file list, in order: their ids come from a correlated
  subquery on the list's table), and the names, joined by ", ", under `<field>__label`;
  `FileCell` (Record UI) draws them. `FieldTypeInterface::isSortable()` (false
  for `file` and `many_to_many`) decides sorting, searching and virtual columns, in the default
  grid, the grid view compiler and the grid source alike.
- **Templates**: the format is `fedale/metadata-driven-template-format` (Packagist;
  `../metadata-driven-template-format` linked to work on it, its own `composer qa`; namespace
  `Fedale\TemplateFormat`): only `symfony/yaml` and `opis/json-schema`. A change to the format
  is made there, with its tests. It describes the field types on its own (`Resources/field-types.v1.json`):
  **a new field type or setting must be added there too**, or
  `FieldTypeCatalogMatchesTheAppTest` fails; and to `translations/field_types.it.yaml`, or
  `FieldTypeCatalogsTest` fails. The comparison of a template's items and the
  version rules (`Fedale\TemplateFormat\Versions`: `ItemStates`, `VersionCheck`) are in the
  format too since v1.1.0, shared with the catalog's check. The `Template` module is the only bridge to the
  metadata; `core.template_item` keeps the id of each exported item across exports (a renamed
  item keeps its id). The install records `ownedState()` as its snapshot, the base of the next
  upgrade. A template requiring others (`RequiredTemplates`): the checker gets their snapshots
  as packages, their ids resolve through their `core.template_item` rows to the names their
  items have now (`RequiredItems`, in `PackageNames` and in `ownedState()`, which must write
  them as ids, never `local:<name>`); what a template requires is read from the manifest in its
  snapshot (`Snapshot::requires()`), not stored apart. After a rolled-back install or upgrade the entity manager is cleared
  (`PersistenceReset`): the ORM would otherwise keep the rolled-back state of changed entities.
- **Security forms**: the stateless CSRF token input needs `data-controller="csrf-protection"` to
  work in a real browser.
